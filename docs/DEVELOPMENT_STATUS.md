## 3. 확정사항과 임시 구현값의 경계

### 3.1. 계속 보존할 사용자 방향

- 모바일 가로형 서바이버, 전장 주력 한 명, 초기 실제 캐릭터 데이터는 비야. 기존 BREAKERS 게임은 변경하지 않는다.
- 비야는 **ART-001 승인 시안 확정 단계에서 보류**. 원화 정합화·3D·리깅·애니메이션·코스튬 제작은 게임의 선행조건이 아니다.
- 레벨업은 기본 서로 다른 무작위 후보3개 중1개 선택. 공통 공격8 + 현재 캐릭터 공격1 + 공통 패시브8(저항 제외) + 현재 캐릭터 필살기 강화1 = **18종**.
- 공통16종을 공유하고 캐릭터 전용2종 및 고유 액티브 설정을 현재 캐릭터 데이터로 교체하는 구조다. 다른 캐릭터 콘텐츠가 이미 완성됐다는 뜻은 아니다.
- 스킬명은 모두 **`[임시]`**. 공격/패시브 보유 상태는 두 줄, 고유 마법은 별도 수동 버튼. 고유 액티브 자체를 19번째 후보로 추가하지 않는다.
- 레벨업 **요구 XP**를 기존의3배로 높인다. 획득 XP3배 지급이 아니다.
- 서포터는 공격2칸·패시브2칸의 빈 자리만. 지원 공격·스탯·저항·수집·뽑기는 아직 미구현이다.
- 환경설정과 상태 반응 방향을 보존한다. 현재 반응은 얼굴 그림이 아닌 문구·테두리 대역이다.

### 3.2. 임시값

공격/패시브 동시 장착 각4칸, 시작 소총Lv.1, 강화상한Lv.5, 후보 동일확률, 개별 이름·공격 형태·피해량·패시브 계수, 마법 MP·쿨다운·범위, 전장 크기·적 수·반응 시간·저체력 경계는 시험값이다. **후보8종을 장착8칸으로 해석하지 않는다.** 명칭·구체 수치의 최종 승인은 없다.

## 6. 기능별 현재 개발 상태

아래는 코드에 작성·연결된 범위다. 모든 게임 기능의 실제 엔진/기기 동작은 NOT_VERIFIED를 전제로 한다.

### 6.1. 기본 전투와 한 판 흐름

- 상태: READY / RUNNING / PAUSED / DEFEAT / CHOOSING / **ABANDONED**. GAME-004C에서 마지막 상태를 추가했고 이전 enum 숫자는 유지했다. 승리 상태·새 보스는 없다.
- 출격은 캐릭터 후보/마법을 검증한 후 위치·HP·통계·적/탄환/픽업/효과·성장/마법/반응을 초기화한다. 잘못된 캐릭터를 비야로 조용히 바꾸지 않는다.
- 터치 이동, PC WASD/방향키·마우스, 경계 제한, 적 생성·추적, 사거리 내 최근접 자동 조준, 선분 기반 탄환 충돌, 관통탄 동일 적 중복 타격 방지 코드를 보유한다.
- 피격 무적 간격을 사용하고 HP0이면 DEFEAT. 결과는 레벨·시간·처치·발사·마법 사용 횟수다. 음량 설정 저장은 있으나 실제 전투 음원은 없다.
- GAME-004C로 진행 중 새 전투/포기 확인, 취소, 포기/패배 구분, 결과→대기를 연결했다. 자세한 보존·무효화 조건은 6.7절.

### 6.2. 성장과 후보 선택

- 적 사망 시 XP 픽업, 접근 시 흡수. 픽업 상한 초과는 마지막 픽업에 값을 합쳐 보존한다.
- 요구량 충족 시 여러 레벨의 선택을 예약하고 CHOOSING으로 정지. 전투 RNG와 추첨 RNG는 별개이며 분류별1개 강제 대신 전체 유효 후보에서 중복 없이 추첨한다.
- 신규 획득/기존 강화, 임시 장착·강화 상한 필터를 사용한다. 설정·상세·이탈 취소는 후보를 다시 뽑지 않는다.
- 성장 ticket은 재시작에도 재사용하지 않는다. 이전 선택·이전 전투·중복 콜백을 거절한다. 한꺼번에 얻은 선택은 순차 처리한다.
- 유효 후보1~2종은 남은 수만 표시. 0종이면 추가 보상/새 스킬 없이 '성장 완료 · 계속'으로 복귀하는 임시 예외다.
- 기본 소총Lv.1은 공격4칸 중1칸. 비야 전용 공격도 공격칸, 필살기 강화는 별도 영역이다.

- 우선순위: 종료 > 피격 > 마법 > 레벨업 > 저체력 > 기본. 낮은 우선순위는 가려진 동안 시간을 쓰지 않고 종류별 한 상태만 보관한다.

- 완성 얼굴·눈깜빡임·전신 동작은 없다. 문구/색/테두리를 최종 라이브 초상화로 보고하지 않는다. 독/화염 지형 반응은 아이디어이며 해당 전투 시스템은 아직 없다.

### 6.6. 모바일 HUD·상세창

- HudLayout이 상단·전장·이동·하단·모달을 함께 계산한다. 넓으면 하단 가로 배치, 좁으면 상태/마법과 스킬 두 줄을 분리한다.
- Android/iOS 안전영역을 논리 좌표로 바꾸는 코드와 빈 값 대체 경로가 있다. 노치/카메라 홀 실기 합격은 아니다.
- 크기 변경은 이동/마법 입력을 해제하고 낡은 마법 요청을 무효화한다. XP·스킬·후보·MP·쿨다운을 초기화하지 않는다.
- 보유 슬롯 상세는 전체 임시명·레벨·설명을 보는 읽기 전용 정지 화면. 빈 슬롯은 비활성, 닫기는 이전 상태 복귀, 획득/강화/발동은 없다.
- 레벨업 카드는3열 또는1열 스크롤. 후보·콜백을 재사용한다. 화면 잘림·컨테이너 최소크기·실제 터치 도달은 미검증이다.

### 6.7. GAME-004C — 이탈·재시작 확인과 결과→대기

**권위:** RunState의 `navigation_ticket`, `transition_action`, `_finished_result`; UI는 `_menu_revision`으로 화면 콜백을 검증한다. 별도 전투 소유자를 추가하지 않았다.

| 입력/상태 | 코드 처리 | 반드시 유지할 경계 |
| --- | --- | --- |
| 설정의 새 전투 시작 | request_transition("restart") → PAUSED 확인창 | 확인 전 HP/MP/XP/보유·선택/통계 초기화 금지 |
| 전투 포기 | request_transition("leave") → 같은 확인창 | 즉시 패배/종료 처리하지 않음 |
| 취소 또는 확인창 Esc | cancel_transition → 이전 RUNNING/CHOOSING | 같은 후보·선택ticket·남은 선택수·RNG와 타이머 보존 |
| 재시작 확인 | 검증 후 현재 캐릭터로 start1회 | 검증 실패 시 원래 전투/확인 유지. UI에서 두 번째 start 금지 |
| 포기 확인 | ABANDONED 및 outcome="abandoned" | HP0 피해로 위장 금지. 보상/승리 조건 추가 없음 |
| 실제 체력 소진 | DEFEAT 및 outcome="defeat" | 포기와 다른 결과 제목/원인 |
| 결과→출격 대기 | terminal에서만 return_to_ready | READY에서 이전 시간 진행 금지. 새 출격 전까지 고정 결과 유지 |
| 확인 중 앱 중단 | intent만 취소, ticket무효화, PAUSED유지 | 자동 재개 금지; 명시적 계속하기 필요 |
| 이전/중복 화면 요청 | navigation_ticket+menu_revision 불일치 거절 | 새 전투를 과거 버튼으로 종료/초기화하지 않음 |

- 상태의 `request_transition`, `cancel_transition`, `confirm_transition`, `interrupt_transition`, `return_to_ready`가 기존 phase와 성장/마법 연결을 재사용한다.
- 미확정 상태에서는 성장 offer/ticket을 건드리지 않는다. **종료 확정 때만** pending/offer를 비우고 성장 ticket을 무효화한다.
- 결과는 종료 시 고정한 Dictionary의 독립 복사본. 호출자가 통계 복사본을 변경해도 내부 기록에 쓰지 못하도록 했다. 재출격은 결과/성장/HP/MP/시간을 기존 초기값으로 새로 시작한다.
- 기존 base main의 메뉴를 재사용하되 시작/계속하기 연결을 가드 콜백으로 교체했다. 포기 결과 제목은 '전투 포기', 실제 패배는 '전투 종료 · 패배'.
- `begin_run()` 자체는 내부 시작 함수로 유지하며 테스트 설정에도 사용한다. 사용자에게 노출된 시작/확인/대기 버튼은 ticket·화면 revision을 검증한다.
- 확인창은 취소 버튼에 초기 포커스를 두고 파괴적 확인을 기본 키보드 포커스에서 제외했다. 실제 입력 전달/버튼 조작은 엔진 미검증이다.
- 새 승리·보스·경제·영구 보상·저장 복구는 추가하지 않았다. 다음 피드백 작업은 GAME-004D이며 이번 완료로 계산하지 않는다.

기존5개 엔진 시험은 이번에 변경하지 않고 새 내비게이션 시험을 그 뒤에 등록했다. 모바일 HUD 입력853×384·960×540·1280×720·1600×720·1920×1080은 작성된 시험 입력이지 합격해상도 목록이 아니다. 합성터치 시험은 물리 기기 멀티터치를 대신하지 않는다.

### 8.3. 실행 경로와 환경 한계

```sh
# 이번 실제 수행: 변경 소스 검사
python tools/check_run_navigation.py
# 기존 별도 HUD 소스 검사
python tools/check_mobile_hud.py
# 엔진 확보 시 전체 검사 (저장 데이터 경로 격리)
python tools/check_project.py --godot /path/to/Godot
# 실제 엔진 개별 시험, 직접 실행은 사용자 설정 경로를 사용할 수 있음
Godot --headless --path . --script res://tests/test_run_navigation.gd
```

check_project는 파일/성장/마법/반응 검사 뒤 엔진이 있으면 import→기반→성장→마법→반응→HUD→내비게이션→시작장면을 실행하도록 작성했다. HUD 및 내비게이션 전용 소스 검사는 별도 명령이다. 엔진없음은 종료2/NOT_VERIFIED, 실제 결함은 FAIL로 구분하며 유료 Actions는 쓰지 않는다.

이번 환경에서 Godot 실행파일을 찾지 못했고 공식 바이너리도 확보하지 못했다. 구문/타입/실행·렌더·Windows·Android·iOS와 실제 입력은 **NOT_VERIFIED**. 전체 check_project 회귀는 **NOT_RUN**. 이후 실행 수단이 확보되면 실제 첫 오류를 고치되, 사용자에게 매번 Pull/로그 제출을 요구하며 코드 작업을 멈추지 않는다. 계속 소스 검사만 늘려 엔진 검증을 대체하지 않는다.

## 11. 다음 세션 인수인계

1. 활성 브랜치와 실제 HEAD를 확인한다. 위 게임코드 커밋 뒤의 문서커밋을 새 게임기능으로 계산하지 않는다. main만 보고 새 프로젝트/새브랜치를 만들지 않는다.
2. CURRENT·본 문서·PLANNED·스킬을 함께 읽고 게임우선/아트보류를 유지한다. 오래된 P0/P0-B와 실패원화/GLB로 자동복귀하지 않는다.
3. NEXT_TASK의 **GAME-004D**를 수행한다. 기존 GAME-004의 전투피드백 후속으로 실제 피해/처치/XP획득 성공을 작은 임시 화면표시에 연결한다. 새 피해수치·확률·적/스테이지·보상 규칙을 만들지 않는다.
4. 시뮬레이션 시간과 개수/수명 상한을 사용하며 선택·상세·설정·확인·결과·대기에서 시간정지, 새출격 초기화를 보존한다. 표시 때문에 피해/추첨RNG/경험치가 달라지지 않게 한다.
5. 현재 mobile_main과 단일 RunState를 계속 사용한다. 엔진 확보 시 기존 모든 시험의 실제 첫 구문/타입/동작 오류부터 처리한다. 미실행을 PASS로 올리거나 검사기준을 낮추지 않는다.
6. 코드·정적·엔진·렌더·모바일을 분리해 보고하고 CURRENT/본 문서/NEXT를 함께 갱신한다. 같은 브랜치에 보존, main자동병합/forcepush/유료Actions/미승인아트 생성 금지.
