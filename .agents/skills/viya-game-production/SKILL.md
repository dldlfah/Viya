# Viya Game Production — 제작 운영 스킬 v1.3

## 최신 우선순위와 문서

**메인 작업문서: `docs/CURRENT_WORK.md`. 누적 개발현황·인수인계: `docs/DEVELOPMENT_STATUS.md`. 통합 후속 계획: `docs/PLANNED_WORK.md`. 다음 게임 단위: `docs/NEXT_TASK.md`.** 개발현황 문서의 존재를 메인 작업문서/README/AGENTS/NEXT에 유지하고 매 세션 읽는다.

**2026-11-26 최신 사용자 지시로 Higgsfield를 이용한 2D 원화 수정·필요한 재생성을 허용한다.** 현재 비야의 흰 외곽선 문제를 원화에서 수정하는 요청과 Higgsfield 사용 재개는 승인된 상태다. 같은 요청의 실행 허가를 다시 묻지 않는다. 과거의 원화 제작 보류·일괄 재생성 금지·크레딧 사용 금지는 이 승인 범위에 적용하지 않는다.

ART-001 디자인 기준과 기존 게임 자산을 보존하고 최신 사용자 작업을 우선한다. 3D 블로킹·리그·코스튬 시스템 제작은 계속 보류하며 과거 P0/P0-B 전체 계획을 자동 재개하지 않는다. 이번 개정은 운영 지침 변경으로 기록하고 원화 생성이나 게임 기능 완료로 계산하지 않는다.

## 사용 조건과 세션 시작

`dldlfah/Viya` 신규 모바일 가로 게임 전용이다. 기존 BREAKERS 본편이나 원작 복원에는 자동 적용하지 않는다. 복원용 스킬에서 진행관리/종료조건/검증/비용통제만 재사용하며 DOS 동등성·원본 주소/RNG 같은 복원 규칙은 전파하지 않는다.

README → AGENTS → 이 스킬 → CURRENT_WORK → DEVELOPMENT_STATUS → PLANNED_WORK → GAME_DESIGN_BASELINE/ART_APPROVAL → NEXT_TASK를 읽는다. 실제 브랜치/HEAD/변경 파일/검증 환경을 확인하며 없는 파일·도구·커밋·실행을 있다고 주장하지 않는다. 최신 사용자 지시와 충돌하는 과거 지침은 대체 관계를 기록한다.

활성 브랜치는 `work/viya-turnaround-qa-20261117`이다. 이름에 아트가 들어가도 현재 게임 코드가 여기 누적되어 있다. 최신 코드 기준과 다음 작업은 CURRENT/DEVELOPMENT_STATUS/NEXT에서 확인하고 실제 HEAD/차이를 대조한다. 과거 GAME-004B/004C 등은 당시 인수인계 이력이다. `main`만 확인해 게임을 새로 만들지 않는다.

## 매 `다음`

1. NEXT와 최신 사용자 요청의 승인된 작업을 진행한다. 게임 작업은 입력 → 상태 변경 → 화면/효과/결과 → 다음 행동까지 연결하며, 명시된 원화 수정 작업은 아래 Higgsfield 절차를 따른다. 작은 수정·검수 문서만 반복하지 않는다.
2. 게임 상태 소유자, 입력, 화면 표현을 분리한다. 현재 시작 장면의 mobile_main 상속 UI와 기존 RunState를 이어 쓰고 원화 미완성을 게임 제작 중단 이유로 삼지 않는다.
3. 변경 범위에 맞춰 리소스·구문·입력·상태·실행을 검증한다. 실행 불가 환경은 NOT_VERIFIED. 실제 오류가 확인되면 해당 오류가 우선이며 미실행을 실패로 단정하지 않는다.
4. 기존 활성 작업 브랜치에서 권한 범위 내 의미 단위로 원격 보존한다. HEAD/미커밋/동시 변경 확인, force push·main 자동 병합·유료 Actions 금지. 메인 작업문서 갱신을 main 브랜치 병합 지시로 오인하지 않는다.
5. **CURRENT에는 최신 사실과 개발현황 문서 안내, DEVELOPMENT_STATUS에는 누적 단계/커밋·기능 상태·파일/수치·검증 증거·미완성, NEXT에는 다음 게임 작업 하나를 함께 갱신한다.** 후속/보류 계획은 PLANNED_WORK에 통합한다. 동일 현황 문서를 계속 갱신하고 세션마다 새 현황 파일을 만들지 않는다.
6. 실제 구현, 검증 범위와 소스 버전, 미검증/미완성, 다음 한 작업만 보고한다. 매회 사용자 Pull·로그를 요구하거나 채팅 밖 자동 작업을 약속하지 않는다.

## 보호할 기준

기존 BREAKERS/REALWONJO/TRIGATE 및 승인 시안 불변. 비야의 성숙한 얼굴·체형·의상·노출 구조·화풍을 임의 재설계하지 않는다. R1/R2와 SAM GLB는 최종 비야로 사용하지 않는다. 게임은 모바일 가로, 주력1명, 향후 서포터2+2 빈칸, 공격/패시브 두 줄, 고유 마법 터치, 반응 영역, 환경설정 방향을 유지한다. 수집·뽑기·과금·다수 캐릭터·서포터 수치를 미리 만들지 않는다.

18종 후보/기본 중복 없는3선택/패시브 저항 제외/스킬명 [임시]/요구XP3배/드롭XP5는 현재 확정 또는 유지 지시다. 동시 장착 각4칸·강화상한5·개별 공격 효과·마법 수치·표시시간은 임시 구현값이다. 전용 자동 공격과 수동 고유 마법을 혼동하거나 후보를19종으로 늘리지 않는다.

## Higgsfield 원화 제작 — 현재 사용 허용

1. **실행 승인:** 사용자가 Higgsfield로 요청한 원화 생성·수정·재생성은 해당 작업의 실행 승인이다. 현재 문제 프레임 수정과 필요한 인접 프레임 정합을 진행하며, 같은 범위에서 부분 편집·시험 생성·필요한 재생성을 할 때 재개 승인이나 같은 허가를 반복 요청하지 않는다.
2. **실제 연결 확인:** 호출 가능한 Higgsfield 도구를 이름과 설명으로 찾고 관련 플러그인 지침을 확인한다. 대화용 도구가 없으면 같은 서비스의 [공식 API 실행기](../../../tools/higgsfield/README.md)도 확인한다. 사용자 태그·이 스킬의 허용·SDK 설치만으로 계정 연결 성공을 판단하지 않는다. API 경로는 인증 값과 허용된 API 접근이 필요하다. 실제 부족한 연결 조건과 생성 미실행을 기록하며, 스킬 금지를 이유로 설명하거나 플러그인을 활성화했다고 주장하지 않는다.
3. **기능·비용 확인:** 연결된 도구의 현재 모델·참조 이미지/마스크·해상도/알파 지원을 확인하고 지원되는 입력을 쓴다. 잔액/견적 조회가 제공되면 확인·기록하며, 조회되지 않는 정보는 미확인으로 남기고 모델/API/비용을 추정해 꾸미지 않는다. 승인 범위의 필요한 작업은 기존 크레딧과 설정된 사용자 비용 한도 안에서 진행한다. 새 결제·자동 충전·요금제 변경이나 요청 범위 밖의 대량 생성은 별도 지시 없이 하지 않는다.
4. **수정 범위:** 승인 디자인과 실제 문제 원본을 구분한다. 얼굴·체형·의상·비대칭·무기·화풍을 유지하며, 흰 외곽선 등 문제 부위와 필요한 배경 여백을 우선 수정한다. 부분 편집으로 해결되지 않으면 사용자가 요청한 문제 원화/프레임을 재생성할 수 있다. 관계없는 캐릭터·방향·전체 자산으로 범위를 확대하지 않는다.
5. **프레임 보존:** 원본을 별도 보관하고 결과를 파생 파일로 저장한다. 투명도/흰 테두리, 수정 범위 밖의 변화, 얼굴/의상/무기, 발/총구·캔버스 등록과 인접 프레임·루프 연속성을 비교한다. 시험 결과를 확인한 뒤 필요한 프레임으로 이어가며 기존 전투·저장·보상 수치를 유지한다.
6. **기록과 승인 상태:** 입력 참조·마스크·모델·설정·작업 ID·비용·전후 결과와 실제 검증 범위를 남긴다. 생성 완료·게임 시범 적용·최종 아트 승인을 구분한다. 도구 제공이나 생성 성공을 캐릭터 일치도/최종 승인으로 간주하지 않는다.
7. **도구 선택:** Higgsfield 지정 요청은 Higgsfield를 우선한다. 다른 이미지 서비스 사용은 사용자의 명시적 선택을 따르며 연결 누락을 이유로 임의 대체하지 않는다. 실제 연결·로그인·필수 입력이 없어 실행할 수 없으면 그 구체적인 전제만 알리고 독립적으로 가능한 원본 조사·수정 자료 준비를 마친다.

## 완료 상태와 증거

PASS는 해당 소스에서 실제 확인한 범위만, FAIL은 재현 결함, NOT_VERIFIED는 미실행/미확인, BLOCKED는 필수 자산·접근 부재로 구분한다. 기본 파일 검사나 생성 완료를 엔진/모바일/아트 합격으로 확대하지 않는다. 코드가 작성돼 있어도 실행을 확인하지 못하면 `코드 작성·연결 / 실제 실행 미검증`으로 남긴다.

개발현황을 갱신할 때 검사 명령·실행 여부·적용 소스·실패/미검증 범위를 함께 적는다. 과거 보고서와 작성만 한 테스트는 이번 실행 증거가 아니다. 최신 실행 근거는 CURRENT/DEVELOPMENT_STATUS의 코드 버전과 함께 확인한다. GAME-004/004B 등의 NOT_RUN은 당시 이력으로 보존한다. 문서 정리만 요청받은 작업에서는 별도 게임 기능 완료·실행 PASS를 부여하지 않는다.
